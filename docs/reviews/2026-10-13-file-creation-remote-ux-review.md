# Duet 파일 생성과 리모트 작업 UX 검토

2026년 10월 13일 기준. 로컬·리모트 새 파일, 새 폴더, 삭제의 구현과 실제 macOS 앱의 입력 흐름을 검토했다. 기능은 이미 있으나 **생성 결과 찾기, 실패 후 수정, 삭제 상태와 복원 안내**가 끊기는 구간이 있다. 우선 데이터 보존과 리모트 경로 처리를 고치고, 생성 대화상자와 결과 선택을 함께 개선하는 순서가 적절하다.

## 검증 범위

- 실행 중인 macOS Duet에서 별도 탭과 `/tmp/duet-ux-review.X3Njfe`를 사용했다. 설치 앱과 현재 소스의 동일 커밋 여부는 확인되지 않았으며, 주요 재현 동작은 현재 소스에서도 원인을 대조했다.
- 한글·공백 이름의 폴더 및 빈 파일 생성, 중복 폴더명, 잘못된 파일명, 필터 중 생성, 폴더 우클릭, 명령 팔레트, 삭제 확인 문구를 직접 확인했다.
- 원래 탭으로 복귀했다. 삭제 확인은 취소했고 기존 사용자 파일은 수정하지 않았다. 임시 폴더에는 검증용 폴더 2개와 빈 파일 1개가 남으며, 앱의 최근 위치와 생성 작업 이력에는 해당 검증 기록이 남는다.
- 앱에 등록된 SSH 호스트가 없고 Docker daemon도 실행되지 않아 실제 리모트 서버 왕복은 수행하지 않았다. 아래 리모트 결함은 코드 분석 결과이며 Windows 실기 재현과 구분한다.
- 소스 변경 전부터 있던 `src-tauri/src/fs/local.rs` 수정은 보존했다. 최초 검토 단계에서는 제품 코드를 변경하지 않았다. 이후 사용자 요청에 따라 아래 개선을 구현했다. 기존 수정은 별도 보존한다.

## 우선 수정할 정확성 문제

### R01 새 파일을 원자적으로 생성하지 않음

**우선순위 P1 · 코드 확인 · 로컬과 리모트 공통.** `create_file`은 `symlink_metadata().is_ok()`로 존재를 확인한 다음 `write_full`로 빈 내용을 쓴다. 확인 직후 다른 프로세스가 같은 이름을 만들면 기존 내용이 잘릴 수 있다. 조회 오류도 모두 미존재처럼 취급한다. 일반적인 중복 이름 방어는 있지만 동시 작업까지 보호하지 못한다.

근거: [core/ops.rs](../../src-tauri/src/core/ops.rs)의 `create_file`, [fs/local.rs](../../src-tauri/src/fs/local.rs)의 `write_full`, [fs/ssh.rs](../../src-tauri/src/fs/ssh.rs)의 `write_full`. 새 파일 Redo에도 같은 패턴이 있다([core/undo.rs](../../src-tauri/src/core/undo.rs)).

개선: `FileSystem`에 기존 항목을 덮어쓰지 않는 생성 연산을 추가하고 로컬·SFTP 구현에 연결한다. 존재 확인은 안내용으로만 사용하고, 최종 생성 연산 자체가 충돌을 거부해야 한다. 권한·연결 오류와 미존재를 구분한다.

완료 기준: 두 동시 생성 중 하나만 성공하고, 기존 파일·심볼릭 링크·조회 오류에서 내용이 보존된다. 생성과 Redo 모두 같은 보호를 사용한다.

### R02 Windows에서 리모트 새 폴더 경로를 잘못 결합함

**우선순위 P1 · 코드 확인 · Windows 클라이언트의 SSH 패널.** `mkdir`은 `parent.path.join(&name)`을 사용한다. Windows의 네이티브 구분자가 원격 경로에 들어가지만 SFTP 전달 함수는 이를 POSIX 구분자로 변환하지 않는다. `/remote/base` 아래 `new`를 만드는 대신 `/remote/base\new`를 보낼 수 있어 실패하거나 잘못된 이름·위치에 생성될 수 있다. 새 파일은 이미 `fs.join`을 사용하므로 두 생성 경로가 일관되지 않다.

근거: [core/ops.rs](../../src-tauri/src/core/ops.rs)의 `mkdir`, [fs/ssh.rs](../../src-tauri/src/fs/ssh.rs)의 `join`·`remote_path_str`.

개선: 새 폴더도 `fs.join`을 사용하고, 이름 검증을 대상 파일시스템 규칙에 맞게 통일한다. 폴더 이름 검증은 현재 빈 문자열과 `/`만 막으므로 Windows 로컬의 `..\name` 같은 입력도 단일 이름으로 거부할 필요가 있다.

완료 기준: Windows→SSH와 macOS→SSH에서 지정한 부모의 바로 아래에 생성된다. 구분자·상위 경로 입력으로 부모 밖에 생성할 수 없다.

### R03 실행 중인 삭제가 취소 신호를 무시함

**우선순위 P1 · 코드 확인 · 로컬과 리모트 삭제.** `fs_delete_execute`가 큐에서 받은 `_cancel_token`을 버린다. 작업 큐는 대기 중 취소만 사전에 처리하고, 실행 중 작업은 각 연산이 토큰을 확인해야 한다. 따라서 이미 시작한 삭제는 취소를 눌러도 계속 진행할 수 있다.

휴지통 삭제 진행률도 `trash_many` 호출 전과 후에만 보고한다. 리모트 다중 항목 이동이나 다른 마운트로의 복사 후 삭제에서는 오래 멈춰 보일 수 있다.

근거: [commands/fs_ops.rs](../../src-tauri/src/commands/fs_ops.rs)의 `fs_delete_execute`, [services/task_queue.rs](../../src-tauri/src/services/task_queue.rs)의 `spawn_worker`, [core/ops.rs](../../src-tauri/src/core/ops.rs)의 `delete_execute`, [fs/ssh.rs](../../src-tauri/src/fs/ssh.rs)의 `move_within_host`.

개선: 적어도 항목 사이에서 취소를 반영하고, 완료한 항목을 저널에 기록한 뒤 종료한다. 중단할 수 없는 OS 호출·원격 복사 구간은 “현재 항목 완료 후 중지”로 표시한다. 리모트는 처리 중인 이름과 완료 개수를 매 항목 갱신한다.

완료 기준: 여러 폴더 삭제 중 취소하면 다음 항목을 시작하지 않고, 이미 휴지통으로 이동한 항목은 복원할 수 있다.

### R04 폴더 생성 Undo가 검사 뒤 재귀 삭제를 호출함

**우선순위 P1 · 코드 확인 · 로컬과 리모트.** `UndoMkdir`은 `fs.list(path).await.unwrap_or_default()`로 목록 오류를 빈 폴더처럼 취급하고, 이어서 재귀 삭제 가능한 `fs.remove`를 호출한다. 빈 폴더 검사 후 다른 작업이 파일을 추가해도 그 내용까지 삭제될 수 있다. 새 파일 Undo의 빈 파일 검사 후 제거에도 동시 편집 경쟁 조건이 남는다.

근거: [core/undo.rs](../../src-tauri/src/core/undo.rs)의 `UndoMkdir`·`UndoNewFile`, [fs/ssh.rs](../../src-tauri/src/fs/ssh.rs)의 `remove`·`remove_recursive`, [fs/local.rs](../../src-tauri/src/fs/local.rs)의 `remove`.

개선: 폴더 Undo는 비어 있을 때만 성공하는 비재귀 제거 연산을 사용하고 조회 오류를 전파한다. 파일 Undo는 변경된 데이터를 복구할 수 있도록 휴지통 사용 등 보존 방식을 검토한다.

완료 기준: 목록 조회 실패 또는 검사 직후 자식 추가 시 데이터가 보존된다. 내용이 생긴 파일의 Undo는 보존 결과와 이유를 정확히 안내한다.

## 권장 구현 순서와 수용 기준

1. **생성·Undo의 데이터 보존과 리모트 경로 수정**: R01·R02·R04. `commands → core → fs` 경계를 유지하고 로컬·SSH 양쪽에 동일한 계약을 적용한다.
2. **생성 대화상자 완성**: R05–R08. 입력 검증 → 진행 상태 → 성공 시 선택 또는 편집 → 실패 시 입력 유지의 흐름을 통일한다. 결과 선택은 원래 요청한 소스·위치·탭에만 적용해, 원격 응답을 기다리다가 다른 탭으로 이동한 사용자의 선택을 덮어쓰지 않는다.
3. **삭제의 상태와 복원 안내 수정**: R03·R11. 취소 가능한 경계와 완료 항목 수를 표시하고 OS별 복원 가능성을 정확히 설명한다.
4. **기능 발견성과 문구 정리**: R09·R10·R12. 생성 메뉴, 폴더 우클릭 대상, 호스트 표시, 단축키 도움말을 맞춘다.

수정 후에는 다음 시나리오를 통과해야 한다.

- 로컬·SSH 각각 파일/폴더 생성, 한글·공백·dotfile, 중복·잘못된 이름·권한 거부·연결 끊김.
- 새 파일 두 동시 생성과 검사 직후 다른 프로세스의 생성·쓰기. 기존 데이터 보존.
- 필터·숨김·이름/수정일 정렬 상태에서도 생성 결과를 찾을 수 있음.
- 느린 SSH 응답 중 연속 Enter·패널 전환·탭 닫기. 중복 작업과 엉뚱한 탭 선택 없음.
- Windows→SSH 새 폴더 생성 후 실제 원격 부모 디렉토리의 항목 확인.
- 리모트 빈 폴더·내용 있는 폴더·다중 선택 삭제, 권한 오류, 다른 마운트, 중간 취소, Undo 복원.
- 폴더 생성 Undo 직전 자식 추가·목록 오류, 파일 생성 Undo 직전 내용 추가. 데이터 보존.

## 자동 검증

백엔드 기존 테스트 17개 통과: `create_file` 1개, `mkdir` 관련 6개, `new_file` Undo/Redo 1개, `fs::ssh::tests` 9개. `cargo test --manifest-path src-tauri/Cargo.toml --lib create_file --locked`로 빌드·실행한 후 동일 테스트 실행 파일에서 나머지 필터를 실행했다. 정상 생성·기존 이름 거부·기본 Undo 및 SSH 경로/오류 헬퍼의 통과이며, R01–R04의 경쟁 조건·Windows 실기·실행 중 취소를 검증한 결과는 아니다.

프론트엔드 `pnpm exec vitest run`: **49개 파일·329개 테스트 모두 통과**. 실행 준비는 `pnpm install --frozen-lockfile`과 `pnpm gen:bindings`를 사용했다. 최초 체크아웃에는 생성 파일 `src/types/bindings.ts`가 없어 이를 먼저 생성해야 한다. 새 의존성이나 제품 코드 변경 없이 검사했다. Node 25의 localStorage 관련 경고가 있었지만 최종 실패는 없었다.

리모트 통합 테스트는 Docker socket이 없어 실행하지 못했다. 기존 `ssh_it_sftp.rs`에는 SFTP CRUD, 파일·폴더 휴지통 왕복, 재귀 제거 테스트가 있으나 이번에 통과했다고 주장하지 않는다.

취소 요청 상태는 진행 모달과 하단 작업 바가 공유한다. OS 휴지통 호출이나 이미 시작한 원격 항목 작업을 강제로 끊지 않으며, 현재 항목/배치 종료 후 다음 항목을 시작하지 않는다. 삭제 진행률은 바이트 대신 완료 항목 수를 표시한다.

새 빈 파일 Undo 중 경합으로 내용이 생기면 휴지통에 남긴다. Redo는 원래와 같이 **빈 파일 생성**이며 휴지통으로 이동한 내용의 복원 기능은 아니다. macOS 로컬 파일은 Finder 휴지통, 리모트 파일은 원격 Duet 휴지통에서 확인할 수 있다.
